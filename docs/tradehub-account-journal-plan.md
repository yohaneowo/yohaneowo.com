## 已定决策（2026-10-22，与站长讨论后；下文各节是完整调研，未选用的部分保留供日后参考）

- **范围**：先做阶段 A，而且 A 包含 Binance **现货＋币本位合约**（币本位是首批用户的主要产品）；U 本位合约、Bybit、OKX、Pionex 进阶段 B。第 11 节全部搁置，不写进开发计划。
- **多用户**：第一版就让任何登录用户绑自己的只读 API，不是只给一个人用。密钥存 admin MySQL、以 Doppler 里的主金钥加密（`TRADE_CREDENTIAL_KEY`），网站永远拿不到明文，只显示 key 的末四码；用户可随时解除。绑定时 admin 先查 key 的权限：开了提现的拒绝，开了交易的警告并建议换成只读 key。
- **同步跑在 admin**（`module_bot/trade/`），照观影统计与 DotaHub 的既有模式：admin 背景同步、以网站帐号 ID 为键、网站用服务端接口只读。所有金额计算在 Python `Decimal` 做，网站只显示。同一个对外 IP 下所有用户共用 Binance 的每分钟权重，由 admin 统一排程。
- **追踪的标的**：Binance 没有「全部成交」接口，只能按标的查，所以每个连接有追踪清单：预设余额不为零的资产 × USDT / USDC 加上有持仓或有过成交的币本位合约，用户可手动加（清仓过的币）。没列入的不算在成本里，页面写明。
- **资料表（第一版五张＋两张合约用）**：`trade_connection`、`trade_fill`（含 product：spot / coinm）、`trade_balance`、`trade_sync`、`trade_position`（合约持仓快照，开仓均价与盈亏先用交易所回报值）、`trade_income`（资金费、已实现盈亏、手续费等合约收支）。订单按成交的 `orderId` 分组，不单独建表。笔记放网站 Postgres。
- **成本口径**：现货用移动加权平均并标注「分析用」；转入没有成本的标「成本未知」。币本位合约按合约乘数（BTCUSD 每张 100 USD）与反向盈亏公式处理，第一版不自行重算均价。
- **美股**：Binance 的「股票」专区（Binance Stocks，2026-06 上线，美股与 ETF，USDC 结算）买的股票不是现货也不是闪兑：持仓以 `EQ_<代号>` 出现在资金钱包，成交与订单走 `/sapi/v1/equity/*`（成交 id 是 UUID、数量可为小数、手续费在订单层）。阶段 A 把它当第三条产品线 `stock` 接进同步；bot 的 `EQ_<代号> → <代号>B/USDT` 对应只是拿来估价的，`<代号>B` 是另一个产品（可铸造赎回的代币化股票 bStocks）。真正在证券商的股票以后才用「手动持仓」补录。
- **沿用 bot 的经验**：bot 的 `/portfolio` 已用 ccxt 读 Binance（现货、资金、理财、币本位钱包、合约持仓）、Bybit、Pionex（原生接口）并把总额快照回报 admin（`bot_portfolio_snapshot`）。admin 的同步也用 ccxt（Python 版，接口相同），Pionex 等 ccxt 不支持的再写原生；余额快照要包含资金与理财钱包，不只现货。交易所资料只有 admin 一个来源，网站与 bot 都是读者；bot 的 `/portfolio` 之后可改读 admin，不再自己打交易所。
- **U 本位合约**：第一版不做，`product` 栏位预留 `usdm`，阶段 A 不写代码。
- **笔记**：第一版最简——一段 Markdown，可挂在一个标的或一笔成交（订单）上，图表与成交列表都能开；截图附件后补。
- **界面**：不开新页面。右侧面板加「账户」分页（余额、持仓、成本、同步状态、绑定管理），下方放成交时间线，图表加「我的成交」开关；同一根 K 线内的成交合并成一个带数字的标记，点开看明细。真实成交与现有模拟交易（paper）是不同资料域、不同图示。

## 1. 产品目标与用户习惯

TradeHub 是用户每天会打开的主要入口，Obsidian 基本不会主动打开。
用户使用 Binance、Bybit、Pionex、OKX，希望通过后端 API 读取自己的账户资料，尤其是：

- 当前资产、现货余额和合约持仓。
- 真实买入、卖出、加仓、减仓的时间、价格和数量。
- 在对应 K 线图上显示自己的成交位置。
- 理解每次操作后持仓、成本与盈亏怎样变化。
- 在看盘时直接记录理由、查看相关笔记和复盘。

核心流程：**看行情 → 查看自己的持仓与成交 → 写计划或说明 → 复盘结果**。

产品定位是个人账户与交易研究工作台。完整性、可追溯性和实际使用频率优先于指标数量、AI 展示或“最强平台”的宣传。

## 4. 第一版范围与非目标

### 第一版

1. 一个只读交易所连接。
2. 历史成交导入与持续增量同步。
3. 现货余额及同步状态。
4. 对应图表上的买卖标记与成交明细。
5. 已知历史范围内的数量、成本和费用展示。
6. 成交关联笔记的最小入口。

### 暂不包含

- 从 TradeHub 下单、改杠杆、转账、提现或管理交易机器人。
- 一次接齐所有账户模式与金融产品。

- 完整盘口热力图、逐笔级策略回测。
- Obsidian 双向编辑同步或复刻日志插件的全部界面。

这些能力可以成为后续独立阶段，不能拖累基础账本与成交展示。

## 5. 页面与交互建议

### 图表工作区

- 中间：现有 K 线图，新增“我的成交”开关。
- 右侧：当前标的在选定账户的资产/持仓、关联笔记。
- 下方：成交时间线、订单分组、持仓变化和日志。
- 后续右侧采用“账户／分析／笔记／助手”切换，避免按每个开源项目单独堆一个分页。
- 筛选：交易所、账户、现货/合约、时间范围、手动/机器人（来源可识别时）。

### 成交标记

- 每笔成交保留实际时间、价格、数量、手续费和来源 ID。
- 可按订单合并显示，但点开后能查看所有部分成交。
- 按当前周期定位到相应 K 线，同时保留原始成交时间与价格。
- 标记归属错误、历史不完整或来源不匹配时不能静默显示为正常。
- 多交易所成交叠加是显式选项，使用来源标签；不能默认画在 Binance 图上而不说明。
- 实盘、模拟和回测数据使用不同数据域与明显标识，不混入同一盈亏统计。
- 大量网格成交按视窗聚合，避免遮住图表；聚合不能丢失底层明细。
- 查看历史成交时，加载对应日期行情；无行情时保留记录并提示覆盖缺失。

### 账户总览

- 各账户余额、可用/冻结资产、合约持仓和估值时间。
- 跨平台币种敞口可汇总，但现货、合约名义敞口和账户权益分开。
- 明确同步成功时间、历史覆盖、限流/断线、待补录及对账差异。
- 私有账户数据仅本人可见，不通过公开分享或公共缓存泄漏。

## 6. 后端架构

建议职责拆分，而非强制某个新语言或框架：

```text
交易所 REST / 可用的私有 WebSocket
                    ↓
后台同步任务：认证、分页、限流、补录、断线恢复
                    ↓
原始事件 + 规范化账本 + 账户快照 + 同步游标
                    ↓
成本/持仓重建、对账、图表聚合、日志关联
                    ↓
登录鉴权后的 TradeHub API 与 React 界面
```

持续同步不能依赖浏览器打开或短生命周期页面请求。按当前部署选择独立 worker、现有 admin 的任务模块或其他长期服务；先确认现有模式再决定，不为此重建整套网站。

个人第一版密钥可由 Doppler 注入后端。若将来允许其他用户自行接账户，再另行设计加密凭据存储、轮换、撤销和用户隔离；不要把个人方案直接推广为多租户方案。

交易所适配层使用统一领域接口，但保留原生差异。是否使用 CCXT 以当前支持程度为准，Pionex 机器人等功能可能需要原生适配。不要假定一个库涵盖所有接口。

## 7. 数据模型建议

以下为概念实体，不是要求按名称机械创建表；应复用仓库已有模型。

| 实体               | 核心内容                                                   |
| ------------------ | ---------------------------------------------------------- |
| ExchangeConnection | 所属用户、平台、账户模式、凭据引用、连接状态               |
| ExchangeAccount    | 主/子账户、产品账户、账户标识                              |
| Instrument         | 平台原始标的、统一标的、产品类型、报价/结算币、合约乘数    |
| Order              | 平台订单 ID、类型、方向、状态、数量与累计成交              |
| Fill               | 成交 ID、订单 ID、时间、价格、数量、费用币种、持仓方向     |
| LedgerEvent        | 充值、提现、划转、资金费、利息、返佣、调整等非普通成交事件 |
| BalanceSnapshot    | 各资产可用/冻结余额、估值来源和时间                        |
| PositionSnapshot   | 合约数量、方向、均价、保证金、交易所报告盈亏               |
| TradeEpisode       | 将多笔成交归入一次交易过程的可重建视图                     |
| JournalEntry       | 正文、标签、策略版本、关联成交/交易过程、附件              |
| DecisionSnapshot   | 当时计划、指标/信号版本、图表截图和数据截止时间            |
| SyncState          | 每账户/产品/标的游标、历史覆盖、任务状态及缺口             |

扩展阶段再按需增加以下实体，不要求第一版建齐：

| 实体                | 核心内容                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------- |
| PatternEvent        | 形态名、版本、参数、标的、周期、发生/确认时间、依据 K 线                                    |
| ResearchRun         | 策略版本、数据范围/版本、费用假设、参数、训练/测试分区、结果与失败状态                      |
| ForecastRun         | 模型与权重版本、输入截止时间、生成时间、预测期限、采样参数和结果                            |
| AssistantRun        | 问题、查询范围、数据截止时间、来源记录 ID、模型版本、回答、耗时与用量                       |
| MetricObservation   | 提供商、指标与口径版本、数值/单位、观察日期、发布时间（如有）、取得时间、延迟状态与修订版本 |
| EventMarket         | 平台及市场 ID、事件条件、YES/NO 定义、截止/结算时间、结算来源、规则版本与状态               |
| EventMarketSnapshot | 报价类型、买卖价差、成交/流动性口径、来源时间、取得时间、原始市场 ID                        |

模型生成文本、数学计算结果与交易所原始事实分开保存；后续修正数据时能识别哪些报告已过期。

技术要求：

- 金额和数量使用精确十进制处理，数据库保留足够精度，避免 JavaScript 浮点累计误差。
- 平台 ID 作为字符串保存，避免超出安全整数范围。
- 统一 UTC 时间存储，显示时转换时区；保留原始时间精度。
- 幂等键包含平台、账户、产品及成交 ID 所需的实际唯一范围。
- 保留受控的原始响应供核对，不记录请求密钥、签名或敏感认证头。
- 派生统计可重算；手写笔记不能被同步任务覆盖。
- 绑定账户权限不能只依靠前端筛选，每个后端查询均验证所属用户。

## 8. 同步与账务规则

### 同步

1. 验证只读连接并确认账户类型。
2. 获取当前余额/持仓快照。
3. 按接口能力分产品、标的与时间范围补录成交。
4. 保存游标与覆盖范围，明确接口无法覆盖的历史。
5. 使用可用的私有流或轮询增量同步；重连后 REST 补漏。
6. 定期重叠拉取并去重，核对余额与持仓差异。
7. 历史不足时提供交易所文件导入或期初余额/成本补录。

不能仅根据当前余额猜测所有历史交易过的币种。需要结合订单/成交接口、已知标的列表与用户导入，说明覆盖边界。

### 账务

- 成交是事实来源，订单状态与账户快照用于关联和核对。
- 现货追加买入、部分卖出、全部卖出要保持费用与库存数量一致。
- 手续费可能用基础币、报价币或第三种币支付；保留原币值，换算口径单独记录。
- 转入资产没有成本资料时标记“成本未知”，不按零成本计算收益。
- 跨账户转账不算交易盈利；有可靠关联才能合并，不确定时显示待确认。
- 当前余额、钱包权益、持仓数量和名义价值不能混为一项。
- 合约需要区分线性/反向、单向/双向持仓、合约乘数、结算币与开平方向。
- 合约追加保证金不是加仓。反手成交可能拆成平仓与反向开仓两段。
- 资金费、手续费、已实现盈亏与未实现盈亏分别列明，避免重复计入。
- 对交易所报告值与本地计算值保留来源和差异，不悄悄覆盖。
- 分批进出如何归为“一笔交易”是产品规则，需可解释；手动和网格默认分组。

## 9. 各交易所适配注意事项

### Binance

- 首先核对实际账户类型和区域适用域名。
- 现货与合约分别同步，不把普通账户、统一保证金等接口混用。
- 优先验证现货部分成交、费用币种、历史补录及余额对账。

### Bybit

- 根据账户模式与 product category 分别查询。
- 单个订单可有多次 execution；相同时间戳不能作为去重依据。
- 核对历史时间窗口、分页游标和私有流恢复规则。

### OKX

- 保留 instrument 类型、账户模式、持仓方向和结算信息。
- 官方成交历史接口有覆盖范围限制，持续采集与历史导入均需设计。
- 资产钱包与交易账户等不同余额范围避免重复汇总。

### Pionex

- 普通余额、订单与成交先独立实现。
- 当前公开文档中存在单独的 Bot reading（Beta）能力；不要假定所有机器人类型及逐笔成交均受支持。
- 用真实账户样本确认普通成交接口是否包含机器人交易、是否可归属机器人。
- 成交接口存在最多返回最新 100 条的情况，需设计时间切片、边界重叠与完整性检查；不能把一次返回当成全量。
- 无法验证完整性的网格盈亏显示“未完整覆盖”，而非伪造完整绩效。

## 10. TradeHub 原生日志与 Obsidian

### 默认体验

用户在 TradeHub 中完成记录与复盘，无需打开 Obsidian。
成交自动导入，只需补充入场理由、预期失效条件、离场理由、情绪和执行偏差。
交易前计划与交易后复盘区分保存；计划修改保留版本或修改时间。

### Obsidian 可选整合

第一步：Markdown 与附件导入/导出，以及 TradeHub 图表定位链接。
第二步：如确有需求，开发本地插件或同步程序，从选定目录同步内容。

- 网站服务端不能直接访问用户电脑的 vault。
- 仅同步明确选择的交易目录，不上传整个知识库。
- 普通 Markdown、图片与内部链接需要渲染/重写支持；Dataview 等插件视图不会自动变成网页功能。
- 第一版外部笔记只读；TradeHub 原生日志在网站编辑，避免双端竞争。
- 用稳定 ID 关联交易和笔记，文件重命名不能造成重复记录。
- 后续如做双向同步，必须加入版本检查、冲突副本、删除策略与附件处理。
- Markdown 渲染应净化不可信 HTML；附件、图片和交易链接遵循私有访问权限。

### Journalit / LucrJournal

二者均是 Obsidian 交易日志工具，不是必须同时安装的独立环节。
目前未确认可供 TradeHub 任意写入的稳定公开 API。
若用户已有数据，先取得去敏样本并检查格式，再做导入适配。
不要因为它们以文件存储，就直接改写其管理目录或承诺兼容专属仪表板。

## 11. 扩展模块与外部项目选型

### 11.1 共同原则

- 功能按用户任务组织，不按 GitHub 项目数量组织。
- 公开仓库、README 宣传、可运行示例和生产可靠性是不同层面的证据。
- 固定引入版本和来源，记录许可证、NOTICE、依赖、权重与数据授权；保留需要的声明。
- 接口、模型能力或许可证未确认的，先标为候选，不把依赖写死在核心业务中。
- 各扩展按需加载、可关闭；失败不影响账户查询、图表与笔记。
- 所有信号、预测和报告显示资料截止时间，避免把旧分析显示为当前判断。

### 11.2 盘口与订单流

- 基础 DOM、成交明细、深度图。
- CVD、足迹图依赖有方向的成交数据，需标明统计范围与缺口。
- 历史盘口热力图需要持续深度采集，不能从 OHLCV 还原。
- 实现本地盘口快照/增量同步、序号检查与断线重建。
- REST 轮询回退不能伪装为连续完整的订单流。
- 账户成交展示与公共市场数据是两个模块，不应互相阻塞。
- 初期只订阅当前标的和少量关注标的；测量频率、带宽、内存、磁盘与前端帧率后再扩容。
- 盘口按交易所和现货/合约分别显示；多平台汇总须明确计价与数量单位。
- 挂单减少可能来自撤单或成交，不能仅凭数量变化判定“主力撤退”或操纵。
- 公开 L2 是价位聚合资料，不等于每个订单或账户身份；隐藏流动性不可完整观测。
- 历史深度采用分层存储与保留策略；开始采集前确定重放所需快照、增量和磁盘预算。
- 回放必须标明数据缺口，不能用插值结果伪装真实订单流。

### 11.3 自定义分析套件与 NVARS

NVARS、支撑压力、趋势过滤和结构标记可作为独立迭代。
保证信号确认时间可追溯，避免用未来 K 线确认的形态在回测中提前交易。
复用开源脚本前验证许可；ChartsLector 指标此前未确认明确授权。

NVARS 是波动调整后的相对强弱指标，不是 RSI 或胜率。实现需要主标的与基准的 OHLC、ATR、滚动累计及 RMS 归一化。
现有比较模块主要保存 close，不能直接承担基准 ATR 计算；还需扩展比较标的配置、OHLC 获取、预热及时间对齐。
先做币对币或同市场比较，缺失交易时段不能任意填零。支撑压力、BOS/CHoCH/FVG 等须分别写清判定规则；K 线识别出的“订单块”不是已证实的机构订单。

### 11.4 蜡烛形态识别

候选参考：`shunjizhan/all-candlestick-pattern-indicators`。
检查时主要实现为 Pine Script v4，依据实体、影线、历史 K 线与均线趋势做确定性规则识别，包含形态筛选、标签和提示。它不是 AI 模型，也不提供已验证的交易优势。

适合 TradeHub 的功能：

1. 图表显示少量用户选择的形态，点击解释条件。
2. 根据币种、周期和趋势筛选，默认避免满屏标签。
3. 在自己的成交旁关联当时已确认的形态，辅助复盘。
4. 后续统计形态出现后的收益分布、回撤和样本量；不直接标成“买入胜率”。

第一版建议：看涨/看跌吞没、锤子/流星、十字星。其余逐项添加。

实现与验收要求：

- 将经确认可用的规则实现为 TypeScript，复用现有指标和绘图机制，不为此引入整套 Pine 运行时。
- 实际规则以代码和产品定义为准；参考脚本有未完成翻译及不准确注释，不能逐字照搬。
- 默认收盘确认；盘中结果只能作为暂定提示，不发重复确认信号。
- 保存规则版本、参数、形态涉及的 K 线和确认时间；回放只使用当前时点可知资料。
- OHLC 缺失、零振幅、均线预热、价格精度及一次出现多种形态均需处理。
- 形态基于原始标准 OHLC，若用户切换 Heikin Ashi 等图表，要明确计算口径，不静默切换。
- 跳空类形态在加密货币上独立验证，不因为股票资料中的解释而直接推广。
- 定义标签碰撞、缩放密度和显示数量限制，确保不遮挡自己的成交标记。
- 统计时预先定义期限、入场价格和过滤条件；重叠信号不当作完全独立样本，报告测试范围与样本量。
- 调研时未在仓库根目录及脚本头找到明确许可证；在未确认授权前不复制或翻译该仓库实现。可独立定义常见形态规则并自行实现，但不复制其代码和说明文本。

### 11.5 带证据的 ASK / 账户复盘助手

这是比同时接入多个买卖评分模型更符合当前需求的 AI 功能，前提是账户账本和日志已经可靠。

代表问题：

- 我这周在四个平台分别买入、卖出和净增加了多少 BTC？
- 这次加仓前后，已知成本和总敞口怎样变化？
- 找出亏损后立即加仓的交易，并说明筛选定义。
- 当时计划的止损是什么，实际有没有遵守？
- 总结这笔交易，链接到每次成交和相关笔记。

建议执行流程：

```text
问题 + 当前标的/账户/时间范围
            ↓
受限的只读工具：查成交、查持仓、查计划、查笔记、调用确定性统计
            ↓
有记录 ID 和数据截止时间的结果
            ↓
模型解释与总结 → 显示来源 → 可保存为报告草稿
```

- 金额、持仓、盈亏和风险计算由程序完成；AI 不自行猜测数值或通过全文心算生成账本。
- 使用明确的只读业务工具，不给模型任意 SQL、终端或交易所写权限。
- 模型请求的账户范围必须在后端再次鉴权；模型不能自行扩大用户权限。
- 资料不全、币种单位不一致或成本未知时说明限制，不能为了完整回答编造结果。
- 默认只读取必要记录；采用外部模型时，应向用户明确哪些账户摘要/笔记会被发送。
- 笔记、网页和导入文字是资料，不是可执行指令；不让其中的提示改变工具权限。
- 回答展示来源链接、统计口径、覆盖范围和时间；链接返回需继续经过用户鉴权。
- 缓存按用户、数据版本与问题范围隔离；记录用量、延迟、取消、超时和失败状态。
- 保存为新草稿，不自动改写既有计划或复盘，不把 AI 猜测保存为成交事实。
- 优先评测结果是否可核对、引用是否正确、未知时是否拒绝编造，而不是回答是否“像专家”。

Ollama 只是可选运行方式。实际模型、上下文长度、隐私要求和速度另行选择；2070 SUPER 8GB 的表现需实测，不承诺所有代理或模型都能流畅本地运行。

### 11.6 策略实验室：Freqtrade 与 Blave Agent

用于以后明确需要的加密货币规则回测和自动模拟，不是本轮多账户账本的必要依赖。
普通 K 线回测不能直接验证盘口级策略；也不能假定它原生完整支持四家平台所有功能。

Blave Agent 是另一个候选参考，重点是策略开发、版本管理、参数扫描、回测验证和运行管理，而不是本项目所需的历史账户账本。
调研时仓库标示 Apache-2.0，并列出 Binance、Bybit、OKX 等平台；未在已测试平台列表看到 Pionex。支持某个平台下单不等于覆盖其全部历史、账户模式与机器人资料。

建议借鉴或单独评估的模块：

- 策略代码和参数版本绑定，每次结果可以重现。
- 参数扫描关注稳定区域，不只展示表现最佳的单个组合。
- Walk-forward、样本外测试及费用假设。
- 运行状态、失败记录、审计和历史结果归档。

已检查的 `lib/validation.py` 中 MCPT 固定仓位序列并打乱远期收益，代码说明该检验本身没有训练/测试分割。
因此较小的 p 值不能作为“未来盈利概率”或替代样本外验证；还需考虑序列相关性、多次尝试与选择偏差。

整合方式：保留 React/Next.js 前端，通过独立任务服务返回结构化结果。不要直接搬入 Electron 桌面壳，也不要为每个研究框架新增一套账户来源。
Freqtrade 与 Blave 先用相同小策略、数据和费用做适配评估，再决定是否复用；不默认同时部署两套执行系统。

执行用户或 AI 生成的策略代码，需要独立受限环境、资源配额和任务超时；研究进程不得持有真实交易密钥或访问生产账户数据库。
本计划仅允许研究、回测和模拟。实盘执行、下单风控、紧急停止及账户写权限应另立需求，不因引用上游项目而自动开放。

### 11.7 预测实验：Kronos、Chronos 与 TimesFM

作为独立 AI 推演实验，不影响账户与日志可用性。
RTX 2070 SUPER 8GB 可作为 small/低批量推理的评估硬件，延迟和显存需实测。
保留预测生成时点、模型版本、输入截止时间及结果；预测数据不进入真实行情和模拟成交数据源。
区间展示需保留采样路径并验证覆盖率，不能把采样比例直接包装成可靠胜率。

可以用 Chronos/TimesFM 作为对照，但统一比较任务：比如未来固定期限的收盘收益或波动，而不是把不同目标的分数直接排名。
通用序列模型若预测 OHLC，需要额外验证价格关系与输入输出设计；不能假定它们天然生成有效蜡烛。

实验协议：

- 固定数据源、时区、缺失处理、标的、周期与预测长度。
- 首先建立“价格不变”等简单基准，按时间划分验证与测试区间。
- 记录模型训练数据覆盖的未知性；持续保存新产生的预测作为前向评估。
- 价格误差、方向表现、区间覆盖和成本后的策略收益分别呈现。
- 不用测试集反复调参后再称其为样本外结果；记录所有试验，不只保存最好一次。
- 评估小批量耗时、峰值显存/内存与排队情况；采样数、预测长度和并发设置上限。
- 推理服务独立部署并可暂停；断开 GPU 主机时账户功能仍正常。

### 11.10 BTC 链上环境：CryptoQuant 与 BGeometrics

目标：为 BTC 日线/周线观察和交易复盘补充市场环境，不作为账户成本来源，也不直接生成分钟级买卖信号。
本节权限数字来自 2026-10-22 的官方公开资料调研，未使用实际账户调用验证；实施当天必须复核，不能将其作为永久免费承诺。

| 来源        | 调研时的免费能力                                                                                  | 当前选择                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| CryptoQuant | Basic：10,000 credits/月、10 次/分钟、日级市场数据、30 天 API 历史；链上 API 从 Professional 开始 | 不以免费方案获取 SOPR/Realized Price；免费市场数据与交易所来源有重叠，暂不优先 |
| BGeometrics | 多种 BTC 链上指标、最多最近 4 年历史；额度小，部分核心指标最近 7 天需订阅                         | 可作个人研究原型，先验证数据覆盖、延迟和授权                                   |

CryptoQuant 的网页历史与 API 历史权限不是同一个概念，不能用免费图表可见范围推断接口权限；credits 也不应直接等同请求次数。

BGeometrics 的文档存在不一致：当前定价页和 Swagger 写 10 次/小时、15 次/天，部分页面仍写 8 次/小时；部分介绍要求免费 key，免费功能页则说明可无 token 使用。
因此适配时核对实际 base URL、认证方式、账户额度与返回头，先按较保守预算调度，不硬编码这些矛盾描述。

最重要的行为：官方更新记录说明 MVRV、SOPR、NUPL、Realized Price 等受限端点的最近 7 天需要有效订阅。免费请求可能成功返回窗口以外的较早资料，而不是报权限错误；相关 `/last` 返回可带 `delayed: true`。
应逐端点验证，不假设所有 STH/LTH 变体或所有指标权限完全相同。

| 指标                   | 解释                                                        | 使用边界                                                 |
| ---------------------- | ----------------------------------------------------------- | -------------------------------------------------------- |
| Realized Price         | Realized Cap 除以供应量；按币最后链上移动时价格形成成本估计 | 不是所有人的实际买入均价，不是用户自己的成本线           |
| STH/LTH Realized Price | 对短期/长期币龄群体计算的链上成本估计                       | 保留提供商的群体划分，不宣称必然支撑/压力                |
| SOPR                   | 被花费输出在花费时与创建时的美元价值之比                    | 反映所覆盖输出的盈亏状态代理，不是所有持币人的盈亏或胜率 |
| MVRV                   | 市值相对 Realized Cap 的比值                                | 用于观察偏离，不能单独确定顶底                           |
| NUPL                   | 市值与 Realized Cap 之差相对市值的比例                      | 不等于账户未实现盈亏                                     |

链上转移可能是钱包整理等非交易活动；交易所内买卖不一定逐笔上链。不同提供商的实体调整、币龄划分和价格源可能不同，不能无说明拼接成一条连续指标。

第一版“链上环境”面板建议先取 Realized Price、STH Realized Price、SOPR、MVRV，权限或额度不够则减少范围。BTC 日线可叠加成本估计线，SOPR 用独立副图及 1.0 基准线；NUPL 等按需要补充。

- 每个指标显示提供商、观察日期、最后成功取得时间、延迟/缺失状态。
- “刚刚刷新”不能掩盖数值属于七天前；延迟数据不可标记成“当前链上状态”。
- 前台只读后端缓存，后台按日及额度调度，不按访客刷新发起上游请求。
- 预算包含历史分页、补录、失败重试；429 退避，不用多个 key 规避额度。
- 获取失败时保留已缓存值并标为过期，不用 0 填充缺失。
- 与现有 `market-panel.tsx` 及 `MarketOverview` 的已实现字段核对，避免重复创建另一套 Realized Price 来源。
- 观察日期、已知发布时间、首次取得时间和修订时间分别保存。历史接口返回值不证明当时已可获得。
- 回测按当时可用资料对齐，免费延迟数据不能回填到原观察日后假装当天可用；无法还原发布/修订历史时明确标注限制。

#### 公开展示与授权

免费读取、付费订阅和公开再发布是不同权限。BGeometrics 当前定价页单列 Commercial Publishing（图表/指标发布）和商业数据再分发边界，条款页面对再分发也有额外限制；各页面不一致时向提供商确认。
CryptoQuant 公开资料也区分再分发授权。初期只在本人私有页面评估，不因为网站本身免费就默认可给所有访客显示供应商数据。
公开发布前确认具体页面展示、缓存、历史保存、导出和原始数据 API 的许可范围。缓存不会自动消除授权限制。

### 11.11 事件预期：Polymarket 与 Kalshi

目标：为当前交易补充“市场当时如何为某个事件定价”，不是增加新的交易账户或下注入口。

- Polymarket 提供公开市场资料接口，可组合市场发现、报价/订单簿和历史资料；按官方端点区分用途与限流。
- Kalshi 官方指南提供无需认证的公开 REST 市场数据访问方式；不能据此认定私有接口或 WebSocket 都无需认证。
- 免费公开读取不等于无限调用、无限历史或自动具有公开再发布权限；实施时核对条款、认证与接口覆盖。
- 先选一个来源接少量事件，验证实际使用价值，再添加第二家。不要自动收录全部体育、娱乐或无关市场。

优先筛选实际存在且与用户交易相关的利率、通胀、监管或 BTC 特定期限价格事件。
页面展示完整事件条件、YES/NO 含义、截止及结算时间、报价类型（买价/卖价/中间价/最后成交）、价差、活跃度、数据时间和原始市场链接。
24 小时变化使用同一种报价口径，历史覆盖不足时不伪造变化值。

#### 解释与匹配规则

- 市场价格是受合约规则、供需、流动性等影响的隐含预期，不是客观发生概率。
- 过时成交价和宽价差不能作为精确概率；无可靠报价时显示“资料不足”。
- 概率变化使用“百分点”与相对百分比分开表达。
- 两平台类似标题不代表相同合约。匹配需核对时间、阈值、是否曾触及/到期收盘、结算价格源、取消或特殊结算规则。
- 未确认等价的市场不做概率平均、不标记套利；展示为不同事件。
- 成交量、流动性和未平仓量采用各平台原始定义，未归一化前不直接跨平台排名。
- 保留规则与状态变化，处理关闭、暂停、取消、结算及结果争议；事件结束后不继续显示成活跃预期。
- BTC 价格事件可能与当前价格高度相关，不应把它当作独立证据重复计入分析评分。

#### 与账户、日志及 ASK 的关联

- 用户记录计划或交易时，可保存相关事件的当时快照，并链接至计划/成交。
- 后续复盘对照实际价格和事件结果；不能拿事后更新的报价覆盖原始快照。
- ASK 引用时同时说明事件条件、期限、报价口径和资料时间。
- 七天前的链上数据、当前市场价格和月底事件报价不能混成同一个“实时共识”。
- 后端为公开市场数据单独缓存，账户/日志关联保持私有；不向预测市场发送用户交易记录。

### 11.12 市场环境模块的边界

账户记录解释“用户做了什么”；链上与事件快照补充“当时能观察到什么”。
两者优先作为复盘上下文，不直接相加为统一买卖分数。
新增供应商前比较与已有资金费率、持仓量、恐惧贪婪、Realized Price 等功能的重叠，复用可用的数据类型和面板。

## 12. 分阶段交付与验收

### 阶段 A：Binance 现货最小闭环

- 只读同步，用户可查看同步状态与历史覆盖。
- 同步重跑不产生重复成交。
- 多次部分成交正确关联订单，图表显示真实成交点。
- 数量与交易所可核对；未知成本明确显示。
- 笔记能关联成交，重同步不覆盖笔记。
- 未登录者及其他用户无法获取账户资料。

### 阶段 B：四平台与合约

- Bybit、OKX、Pionex 分别通过脱敏样本和实际只读对账。
- 现货与合约、主子账户、机器人分类可筛选。
- 加仓、减仓、平仓、反手和追加保证金区分正确。
- 历史缺口与机器人覆盖限制可见。
- 同步服务重启、限流和断线后能够恢复，且不产生重复记录。

### 阶段 C：日志与复盘

- TradeHub 内直接写计划、成交说明和复盘，支持截图附件。
- 查看标的或成交时能看到对应笔记。
- 分开呈现费用、已实现和未实现盈亏及统计覆盖范围。
- 同类交易统计展示样本数，实盘/模拟/回测不混算。
- Markdown 与附件导出可验证恢复，不只是生成看似成功的文件。

### 阶段 D：形态分析与账户助手

- 第一组形态有明确算法、收盘确认、预热和边界用例；许可问题已解决。
- 形态标签不遮挡成交标记，回放不能读取未来 K 线。
- ASK 的数值与账本计算一致，每个核心结论可跳转到来源。
- 数据不足、未知成本、跨用户查询、笔记提示注入和模型服务失败均有可验证行为。
- AI 回答保存为独立草稿，不覆盖交易事实或用户计划。

### 阶段 E：盘口与订单流

- 先当前标的 DOM/成交明细，再 CVD/足迹图，最后历史热力图。
- 验证快照与增量合并、序号缺口、断线重建和数量单位。
- 页面显示数据来源、延迟和缺口；不得以轮询或插值伪装完整逐笔流。
- 在约定的标的数和保留期下测量带宽、磁盘、内存与交互流畅度，再确定容量目标。

### 阶段 F：可选 Obsidian 桥接

- 先验证选定目录的只读导入，再决定是否自动同步。
- 笔记重命名、重复导入与附件路径有明确处理。
- 无已有 Obsidian 数据需求时可跳过；不把它设为阶段 D/E 的前置条件。

### 阶段 G：策略与预测实验室

- 先选一套策略研究流程和一个预测模型，完成最小对照实验。
- 每次运行有数据、代码/模型版本、参数、费用与样本外范围。
- 失败和不理想结果保留，不只展示最优参数；报告基准、样本量和已知限制。
- 推理和策略任务可以取消，资源受限，不能访问交易写权限。
- 只有结果和日常使用证明有价值，才增加其他模型或多代理分析。

### 阶段 H：可选链上环境与事件预期

- 先用少量链上指标或精选事件验证价值，不要求四个供应商全部接入。
- 已核验免费范围、实际数据日期、限流、历史长度与当前展示的授权范围。
- 成功返回旧值、`delayed` 标记缺失、429、超时、缺数据时均能正确呈现状态。
- 链上指标不混用供应商口径，回测使用可用时间而非简单观察日期。
- 事件报价标明类型与规则，能处理宽价差、无成交、关闭和结算。
- 不等价事件不得自动平均；数值单位、百分点和时间窗口验证通过。
- 交易关联的环境快照可追溯且不被后续更新覆盖；ASK 引用真实来源。
- 页面刷新不重复消耗上游额度，私有账户关联不进入公共缓存。

阶段顺序是建议，不是把每个阶段列为必做任务。A 是后续账户功能基础；C 为 ASK 提供日志资料；E/H 可在独立公共行情链路上推进；F 完全可选。H 的基础展示不依赖 G 的模型实验，交易复盘关联依赖核心账本和日志。

## 13. 测试重点

使用脱敏响应与可复现夹具验证：

- 一个订单多次成交、同时间戳多成交、重复事件、乱序与补漏。
- 基础币/报价币/第三币手续费，精度与舍入。
- 部分卖出、全部卖出、转入成本未知、跨账户划转。
- 单向反手与双向持仓，保证金调整与成交区分。
- 历史分页边界、接口截断、限流恢复与游标持久化。
- 图表周期聚合、实际成交时间保留及不同市场来源标记。
- 私有 API 越权、公开缓存污染、附件访问与 Markdown 渲染。
- 同步过程中笔记不被覆盖；导出可读、导入幂等。
- 形态在盘中/收盘、数据缺失、预热和零振幅时的行为；历史回放无未来信息。
- ASK 数值、引用、账户范围、过期资料提示、提示注入及模型不可用时的降级。
- 研究任务可复现、测试集不参与调参、基准对比和费用计算。
- 本地盘口乱序/丢失/重连；CVD 与热力图缺口提示。
- 数据库和附件备份恢复、worker 重启恢复、停用连接后的同步停止。
- 链上数据“请求成功但数值延迟”、修订、额度耗尽、分页与日预算；回测时间对齐。
- 预测市场报价类型、事件规则差异、流动性不足、结算状态变更与历史快照保留。
- 指标和事件来源在 ASK 中有正确日期与口径，不把旧资料表述为实时事实。

每个阶段先写可测量的验收项，再实现。性能阈值根据部署机器和真实数据规模确定，本文不虚构毫秒级延迟或支持用户数。

不要为了验证只读同步提交真实订单。日志与错误信息不得包含 API secret、签名或完整敏感响应。

## 14. Claude Code 开始实施时的建议流程

1. 重新检查仓库当前实现、未提交变更与适用指引。
2. 确认本次要执行的阶段；默认先拆阶段 A，不一次实现整篇路线图。
3. 根据最新官方文档和实际账户模式确定接口，列出历史与账户覆盖限制。
4. 设计最小数据模型、同步生命周期和成本口径，再实现图表与日志入口。
5. 所需凭据由用户在约定的密钥系统配置；不要要求把 secret 粘贴到聊天。
6. 完成 dev 验证、对账与必要测试，报告修改文件、验证结果和剩余限制。
7. 遵循仓库的提交与部署约定；未明确要求不 commit/push、不合并 main。

每个阶段交付时说明：本次范围、实际接入的数据与权限、迁移与恢复方法、测试/对账证据、未覆盖情况、后续依赖。
新增外部项目依赖时记录固定版本与许可结论。不要将本文中的调研判断当成完成代码审计或实际性能测试。
